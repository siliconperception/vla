1. BASELINE
--------------------------------------------------------------------------------
Command (checkpoint.pt.wnotap, 100K steps, log/exp.wnotap):

  python vla.py --dataset web --preroll --tokenizer pythia31m \
    --context 16 --n_hidden 256 --kernel 3 \
    --batch 250 --monitor 20 --checkpoint 5000 \
    --opt sgd --momentum 0.0 --weight_decay 0.0 \
    --schedule const --lr_max 0.01 --seed 1 \
    --n_layers 7 --depth 7 --clock fixed --clock_base 2.36 \
    --init gaussian --ema 0.5 --accumulate \
    --run_steps 100001

  29.4M trainable params.  No --tap: the DFF register receives ContextCNN's
  output directly (post-BatchNorm, post-ReLU), so it is bounded by construction.
  Clock ladder at --clock_base 2.36, n_layers 7: 1,2,6,13,31,73,173 steps.
  Throughput ~2.9 steps/s on the RTX 4090.  --batch 250 == 250 tokens/step,
  so 5K steps == 1.25M tokens and a 100K run == 25M tokens.

3. WHAT IS ALREADY ESTABLISHED (do not re-litigate)
--------------------------------------------------------------------------------
a) Optimizer: plain SGD, lr 0.01, momentum 0.  AdamW parks at the unigram floor
   for thousands of steps with dff_max excursions to 3.7e5.  A 200-step lr x
   momentum grid on web put lr 0.01 / momentum 0 at the best state behaviour
   (dff_max 29-37) with healthy descent.  lr 0.1 blew dff_max to 6e5.
b) Reach is set by the slowest layer's write period:
       reach ~ kappa(ema) * p_max,   kappa(a) = ln(0.05)/ln(1-a)
   Confirmed on three configs; it OVERESTIMATES by 2-3x in practice.
   At --ema 0.5, kappa = 4.32 writes.  --clock_max is a dead lever (E[h] grows
   only as log2 of the cap; document scale would need cap ~ 2**88).
c) Measured reach, warm-context probe, openwebtext:
       --clock exp,   ema 0.5   ->  saturates by c ~ 8-16   (a 10-gram)
       --clock fixed, base 2.36 ->  still +0.209 nats at c=64, +0.107 at c=96
d) Teacher-forced loss cannot see free-running collapse.  Generation can lock
   into a repeating token while held-out loss improves; --clip_dff rescues it.
e) Runaway rate is NON-MONOTONE and excursions are universal, not a property of
   any one option (wfix236 hit 100% at 50K and recovered to 8% by 65K; wnotap
   hit 46% at 40K and recovered to 0.8%).  Never call a trend from two points.
f) Checkpoints must be read with score.py's stable_load(): torch.save is not
   atomic and a mid-write read scores as a broken model without raising.

4. SEARCH ALGORITHM
--------------------------------------------------------------------------------
  1. From results so far, form a hypothesis that changes exactly ONE vla.py
     command-line option relative to the current baseline.  Write down the
     prediction and what result would falsify it BEFORE running.
  2. Run the experiment.  Length is a multiple of 5K steps, chosen from the
     hypothesis (see per-experiment "budget" below), not fixed in advance.
  3. Analyze.  If the change wins on the decision rule in section 6, it becomes
     the new baseline and subsequent experiments build on it.  If it loses,
     record why and return to step 1.

  Single-option discipline is the point: it keeps every result attributable.

  WHEN THE BASELINE CHANGES, RE-EXPRESS THE WHOLE QUEUE.  Every pending
  experiment must be exactly ONE change from the CURRENT baseline, not from the
  one it was written against.  After any PROMOTE:
    - walk the queue and rewrite each entry relative to the new baseline
    - DROP any entry that the promotion already answered, or that is no longer a
      single change (e.g. if --init zero is promoted, an entry reading
      "--init zero" is now the baseline and must be deleted, while one reading
      "--init relu" is still a single change and survives with its comparison
      numbers updated)
    - UPDATE every baseline number quoted in a prediction or falsifier: the loss
      thresholds in section 2, the reach figures, the runaway rates.  A falsifier
      written against stale numbers is worse than none, because it looks valid.
    - RE-DERIVE the order: a promotion changes which dimensions are still
      uncovered, and coverage drives the order (section 6c).
  Record in the running log which baseline each result was measured against.
  Without that, results from before and after a promotion are not comparable and
  the whole point of the single-option rule is lost.
  Where an option is only meaningful together with another (e.g. changing
  --n_layers moves p_max unless --clock_base is renormalized), that is called
  out explicitly and the pair is treated as one conceptual change.

5. REPORTING PROTOCOL (every 5K-step checkpoint, no exceptions)
--------------------------------------------------------------------------------
  - loss (mean of last 10 monitor lines), and the gain over the previous 5K block
  - grad: direction matters more than level (see 6b).  Report the SLOPE per 10K,
    not just the value.  Rising = the deep stack is still organizing and more
    tokens will pay.  Flat = the configuration has finished.  Collapsing to a
    constant while loss is flat = drowned token, stop.
  - dff_std, dff_max, dff_zeros.  dff_max climbing while dff_std is flat is the
    outlier-channel signature.
  - free-running generation health: exp/gencheck.py, 3 fresh samples.
    cycle > 0.6 == degenerate.  Healthy is 0.08-0.11.
  - SUBJECTIVE ANALYSIS OF GENERATED TEXT.  What to look for, in order of the
    development already observed: word-shaped tokens -> local bigram/trigram
    coherence -> correct function words -> clause-level syntax -> contractions
    and punctuation conventions -> <ETX> emitted on its own -> discourse
    connectives placed correctly (these require prior context) -> pronoun and
    referent persistence across a sentence boundary -> topic maintained across
    paragraphs.  That last pair is the qualitative counterpart of the reach
    measurement and is where long- and short-reach configurations diverge.
    Report what is present, what is absent, and what changed since last time.
    One sample at temperature 1.0 is a noisy draw -- do not build a case on it.
  - every 20K: exp/score.py (clean, median, runaway%) and exp/reach.py.

6. DECISION RULES
--------------------------------------------------------------------------------
  PRIMARY   held-out clean loss at matched step count.
  PRIMARY   token efficiency: steps to sustained crossing of 6.5 / 6.3 / 6.1.
  GATE      free-running generation must not be degenerate at the final ckpt.
  SIMPLER   On EQUIVALENCE, the simpler configuration WINS -- this is a rule, not
            a tiebreak.  If a result is within sigma (~0.07) of the baseline and
            the configuration is simpler, PROMOTE it.  Do not keep complexity
            that has not paid for itself.  "Simpler" means, in rough priority:
              removes a module or a mechanism entirely
              fewer trained parameters
              fewer non-default flags (closer to a plain vla.py invocation)
              smaller state, less compute, fewer moving parts at inference
            This applies to the model AND the training procedure: a schedule, an
            optimizer setting or a probe that can be dropped without measurable
            cost should be dropped.  The target is an FPGA dataflow
            implementation, so every retained module is hardware -- simplicity is
            a first-class objective here, not an aesthetic preference.
            Corollary: actively PROPOSE simplifications.  An experiment that
            REMOVES something is worth more than one that adds something, at
            equal expected effect, because a tie still advances the design.
  NOISE     run-to-run sigma on loss is ~0.07.  A margin under 0.07 is a tie;
            resolve ties by simplicity, not by picking the lower number.
  RUNAWAY   report it, do not act on a single reading (see 3e).  Only a rate
            elevated at three consecutive milestones counts as a trend.

6b. DIRECTIVE -- GRADIENT TREND AS THE EXTRAPOLATION METRIC
--------------------------------------------------------------------------------
Working hypothesis (user, 2026-08-21): as long as the gradient norm is stable or
slowly growing, the loss will keep coming down.  Corollary: a flattening or
collapsing gradient says the run has extracted what this configuration can get,
and more tokens will not help.

Why it matters: the final run may train for ~1B tokens (4M steps at --batch 250,
about 16 days at 2.9 steps/s).  Nothing in this search runs that long, so every
recommendation is an EXTRAPOLATION from runs of 20-100K steps.  Loss curves at
that length are nearly parallel and cannot distinguish "still descending" from
"about to flatten".  The gradient trend can.

Evidence, 16 non-overlapping 10K windows from wnotap / wexp / wfix236 /
e01_ema25 (windows before 10K excluded, they contain the breakthrough):

    corr(grad_slope, loss_gain) = -0.690
    grad rising  (slope > 0): loss fell in 13/14 windows
    grad falling (slope < 0): loss fell in  2/2 windows

  and at the extremes, which is where it is most convincing:
    every AdamW run that parked at the unigram floor had grad COLLAPSED to a
      flat ~1.0 while loss did not move for thousands of steps
    wexp had grad flat at 4.55-4.92 from 10K on, and its per-5K gains decayed
      0.72 -> 0.215 -> 0.150 -- a configuration that had finished
    wnotap still had grad creeping up at 60-80K and was still gaining
    the 2026-06-09 SGD run: grad decayed to 1.12, sat flat ~8000 steps, then
      GREW 1.2 -> 1.6 -> 2.3 -> 6.5 and the loss collapsed 3.5 -> 1.0 in 200
      steps.  Rising grad LED the breakthrough by ~1000 steps.

CAVEAT, do not overstate this: the correlation is measured across pooled windows,
and early windows have both a rising gradient and a fast-falling loss, so part of
the association is simply "early vs late" rather than gradient predicting loss.
With n=16 it cannot be controlled for.  Treat a rising gradient as evidence that
more training will pay, not as proof, and never as a reason to ignore a loss
curve that has visibly flattened.

SCOPE -- READ THIS BEFORE USING IT (user, 2026-08-21):
  Gradient is a SECOND ORDER effect and a HEALTH CHECK.  It is not a ranking
  criterion and must not be weighted against loss.  LOSS IS WHAT MATTERS.  An
  earlier draft of this section said to prefer a configuration with a rising
  gradient over one with a marginally lower loss; that was wrong and is retracted.

HOW TO APPLY
  - Report grad trend (slope per 10K) at every checkpoint as a HEALTH LINE,
    alongside dff_max / dff_std / dff_zeros.  It answers "is this run alive and
    still organizing", nothing more.
  - The one strong signal, because it is a failure mode rather than a ranking:
    a COLLAPSED gradient sitting flat while the loss does not move is the
    drowned-token signature (every AdamW run that parked at the unigram floor had
    grad pinned near 1.0).  That is a reason to STOP.
  - EXTEND on the loss curve: extend when loss is still falling.  A rising
    gradient is at most weak corroboration that there is road left.
  - Do NOT rank configurations by gradient slope, do NOT promote or reject on it,
    and do NOT quote it as the basis of an extrapolation.  Compare loss at the
    latest step both configurations have reached, plus the held-out score.
  - Windows shorter than ~10K are too noisy to read at all: on 5K windows E17 and
    the baseline both read -0.4/10K, and on 5K-15K the baseline reversed to
    +0.151 while E17 sat at -0.004.  If it is reported, use >=10K windows.

6d. DIRECTIVE -- EARLY SPEED DOES NOT PREDICT THE FINAL FLOOR
--------------------------------------------------------------------------------
Lower early loss does NOT imply lower final loss.  The two can anti-correlate,
and this search has already produced examples in both directions.

  ssync on tiny broke through EARLIEST of the clock group (step 860 against
    sbase 1280, sincr 1700) and had the best training loss -- and it was the one
    configuration that was unusable, diverging at inference position 99.
    sincr broke through LAST and had the best held-out loss of the stable ones.
  E01 (--ema 0.25) crossed the unigram floor at 1280 steps against the baseline's
    3980, a 3x speedup -- and by 30-35K the train-loss margin was 0.025-0.032,
    inside sigma.  The whole advantage was banked before 20K and then decayed.
  E17 (--init zero) crossed at 1340, also ~3x, and its loss at the matched 5K
    step is 0.25 WORSE than the baseline's.  Faster to the threshold, behind on
    the curve.

WHY IT HAPPENS HERE: the early phase is dominated by how quickly the stack
escapes the unigram plateau, which is a transient.  The late phase is set by what
the configuration can represent.  Nothing forces those to be the same ordering,
and the DFF state options (--init, --ema) plausibly affect the first much more
than the second.

HOW TO APPLY
  - steps-to-threshold at HIGH thresholds (7.549, 7.0, 6.5) measures escape from
    the plateau.  Report it, but do NOT treat it as evidence about final loss.
  - the token-efficiency objective is about reaching a LOW loss, so weight the
    6.1 / 5.9 / 5.8 crossings and the best level actually achieved.  A
    configuration that reaches 7.0 in half the tokens and stalls at 6.3 is worse
    than one that is slow to 7.0 and reaches 5.8.
  - never TERMINATE for slow early progress while the gradient is rising
    (section 6b).  That is the signature of a stack still organizing, and it is
    exactly the case where early loss is least informative.
  - conversely, do not PROMOTE on an early-step win.  Require the comparison at
    the latest step both configurations have reached, plus the held-out score.

6c. DIRECTIVE -- SEARCH STRATEGY: COVERAGE, NOT HILL CLIMBING
--------------------------------------------------------------------------------
The stated goal is "collect many diverse and comparable data points to help guide
the optimization".  That is NOT hill climbing.  A greedy descent gives you one
trajectory through parameter space and tells you almost nothing about the
landscape -- it is close to the least informative way to spend a small number of
expensive runs.  Diverse, comparable points let us REASON about which dimensions
matter, which is the only way to extrapolate to a run (~1B tokens, ~4M steps,
~16 days) that will never be done at this scale.

Sample budget is ~10-20 experiments at ~4 h each.  At that n, the difference
between an optimally ordered greedy search and a randomly ordered one with an
accept-if-better rule is almost certainly smaller than the run-to-run noise
(sigma ~0.07).  Elaborate ordering schemes optimize a term that rounds to zero.

WHY NOT TO TRUST A PRINCIPLED ORDERING HERE, SPECIFICALLY
  Any ordering rests on a prior about which options interact and which set the
  achievable floor versus the rate of approach.  That prior has been wrong
  repeatedly in this study:
    - predicted --ema 0.25 would converge SLOWER; it reached the unigram floor
      in 1280 steps against the baseline's 3980
    - predicted removing --tap would cost reach; it doubled it (mean excess
      +0.0756 vs +0.0359)
    - called a trend from two points three separate times, once cancelling a
      healthy 100K run
  Randomized or opportunistic proposal order has a real virtue here: it breaks
  the correlation between that prior and what actually gets tested.

WHAT TO KEEP FROM THE ORIGINAL PLAN (all cheap, all load-bearing)
  - PRE-REGISTERED PREDICTIONS.  Free to write, and the only reason the --ema
    surprise was legible as a surprise instead of being quietly absorbed.
  - NEVER RE-RUN A DECIDED QUESTION.  Section 3 exists for this.
  - ONE CHANGE PER EXPERIMENT.  This is what makes points COMPARABLE, which is
    the user's actual stated criterion.  It is the rule, not a heuristic.

WHAT TO DROP
  - Phase structure, and any claim that a given option must be tuned at a
    particular position in the sequence.
  - Deep greedy descent on whichever dimension just produced a result.

THE BIAS TO APPLY INSTEAD: COVERAGE
  Prefer the next experiment on a dimension with ZERO data over another step
  along a dimension that just moved.  Dimensions and their current coverage:

    --ema            E01 running (0.25 vs 0.5)          some
    --clock/base     several points on tiny, 2 on web   some
    --tap            wnotap vs wfix236                  decided (off)
    --n_layers/depth 7x7 only on web                    NONE on web
    --context        16 only, every run ever            NONE
    --n_hidden       256 only, every run ever           NONE
    --schedule       const only, every run ever         NONE
    --batch          250 only, every run ever           NONE
    --lr_max         200-step grid only                 WEAK
    --init           gaussian on web only               NONE on web
    --accumulate     on, always                         NONE on web
    --qproj          none, always                       NONE

  Five dimensions have never been touched at all.  A single point on each is
  worth more than a fourth point on --ema.

ON LEARNING RATE, since it is the natural thing to want to tune first or last:
  Neither.  VALIDATE it early and cheaply -- 0.01 was chosen from a 200-STEP grid,
  which is weak evidence for 100K runs, and every comparison downstream inherits
  it.  OPTIMIZE it late, on whatever architecture is settled and at the horizon
  that matters, because that is when the tuning is worth spending on and when it
  will not be invalidated by a later structural change.

ONE REDUNDANCY WORTH KNOWING BEFORE PROPOSING REACH EXPERIMENTS
  reach ~ kappa(ema) * p_max, so --ema and --clock_base are redundant along the
  reach axis and their PRODUCT is what matters.  Optimizing them separately by
  coordinate descent is precisely where a greedy search gets stuck.  Reach is now
  a SATISFIED CONSTRAINT (wnotap mean excess +0.0756, well past document scale),
  so do not spend further runs increasing it.  The open question is the reverse:
  at MATCHED reach, does trading p_max down against ema down buy loss?  Surplus
  reach may be costing accuracy, since a 173-step layer writes only ~578 times in
  100K steps and is chronically under-trained.

7. EXPERIMENT QUEUE
--------------------------------------------------------------------------------
Ordered by COVERAGE first (section 6c): a dimension with no data outranks a
further point on one that just moved.  Each is one option off the CURRENT
baseline.  Re-derive the order after each result, and expect it to be partly
opportunistic -- that is intended, not a failure of planning.

CURRENT ORDER (2026-08-21, after the wnotap reach result and 6c):
  running  E01  --ema 0.25            finishes 40K, then decide
  next     E05  --schedule cosine     zero data on this dimension, and the
                                      largest known lever on FINAL loss
  then     E10  --context 24          zero data; attacks the 6.08 plateau from
                                      the capacity side rather than the rate side
  then     E11  --lr_max 0.02         cheap validation of a value picked from a
                                      200-step grid; protects everything after it
  then     E06  --batch 500           zero data; the direct knob on the
                                      tokens-to-loss objective
  then     E15  --n_layers 3 --depth 17 --clock_base 13.15   WIDE bracket, low end
  then     E16  --n_layers 17 --depth 3 --clock_base 1.38    WIDE bracket, high end
  then     E07/E08 shape              5x10 and 10x5, the NARROW bracket
  then     E02 --init relu, E03 --no-accumulate, E09 --qproj read, E12 --clock incr
  deferred E13  --ema 0.10            a fourth point on a dimension that already
                                      moved; worth less than any of the above
  deferred E14  matched-reach trade   (see 6c) --clock_base 2.0 with --ema 0.25,
                                      i.e. p_max 64 x kappa 10.4 = reach ~666,
                                      the baseline's reach by a different route.
                                      Tests whether surplus p_max costs accuracy.
                                      Deferred because reach is already satisfied
                                      and this is a two-flag change.

E01  --ema 0.25          budget 40K   ~3.8 h
     Hypothesis: --ema 0.5 keeps only kappa=4.32 writes, so even the 173-step
     layer retains ~4 writes.  0.25 gives kappa=10.4, roughly 2.4x the reach.
     Predict: reach at c=64/96 up; loss neutral to slightly worse early
     (a lower ema adapts more slowly), better after ~30K.
     Falsified if: reach curve is unchanged, which would mean ema is not the
     binding constraint at this p_max and the formula is wrong for --clock fixed.
     WHY FIRST: --ema is the cheapest reach lever, is in the original option
     set, and has never been varied on web.

E02  --init relu         budget 20K   ~1.9 h
     Hypothesis: without --tap the register holds a rectified, nominally sparse
     value, so relu(randn) is the matching seed; gaussian was chosen FOR the
     dense tapped register.  Note dff_zeros falls 0.51 -> 0.02 within 10K, so
     the register is dense in steady state and this may be inert.
     Predict: faster early convergence (fewer steps to L<7.0), no change late.
     Falsified if: steps-to-7.0 within 200 of baseline (5940).
     Cheap, and it tests whether the init still matters once --tap is gone.

E03  --no-accumulate     budget 40K   ~3.8 h
     Hypothesis: with p_max=173, --accumulate commits the MEAN of up to 173
     outputs -- heavy smoothing that may erase the fine detail the slow layers
     are supposed to carry.  Sampling one output instead may sharpen them.
     Predict: worse early (noisier writes), better reach detail late.
     Falsified if: loss worse at every milestone.

E04  --clock_base 2.0    budget 40K   ~3.8 h
     Hypothesis: 2.36 was solved for reach ~750 on 890-token documents, but the
     formula overestimates 2-3x, so the true reach is ~250-350 and p_max may be
     larger than useful.  base 2.0 gives ladder 1,2,4,8,16,32,64.
     Predict: faster convergence (slow layers train 2.7x more often), shorter
     reach.  This directly measures the reach/token-efficiency trade.
     Falsified if: both loss and reach worse -- there is no trade, just a worse
     setting.

E05  --schedule cosine   budget 100K  ~9.6 h
     Hypothesis: every result so far is on --schedule const.  A decaying lr is
     the single largest known lever on FINAL loss in LM training, typically
     0.1-0.3 nats, and it costs nothing in tokens.
     Predict: 100K final well below 5.78; most of the gain in the last 30K.
     Falsified if: final loss within 0.07 of const.
     NOTE: not a fair comparison at intermediate steps -- judge only at the end,
     and only against a const run of the SAME length.
     Run this LAST, after the architecture is settled: it is the most expensive
     and it interacts with nothing.

E06  --batch 500         budget 40K   ~3.8 h (2x tokens/step)
     Hypothesis: the second objective is tokens-to-loss, and batch is the direct
     knob.  250 rows may be past the point of diminishing returns per token.
     Predict: better loss per STEP, worse or equal per TOKEN.
     Falsified if: better per token too -- which would mean the gradient is
     noise-limited and batch should go up further.
     IMPORTANT: this is the one experiment where step-matched comparison is
     wrong.  Compare on the token axis (steps x batch).

E07  --n_layers 5 --depth 10 --clock_base 3.63   budget 40K  ~3.8 h
     Two options move together on purpose: base is renormalized so p_max stays
     at 173 (b = 173**(1/4) = 3.63, ladder 1,4,13,48,173) so that only the
     NUMBER of timescales changes, not the reach.
     Hypothesis: 7 layers x depth 7 was inherited, never justified.  Fewer,
     deeper layers = fewer registers but more compute per timescale.
     Predict: small effect either way; informative because it separates "number
     of timescales" from "reach", which no experiment has done.

E08  --n_layers 10 --depth 5 --clock_base 1.77   budget 40K  ~3.8 h
     Mirror of E07: b = 173**(1/9) = 1.77, ladder 1,2,3,6,10,18,31,55,98,173.
     More registers, shallower each, same reach.  E07 and E08 bracket the
     baseline's 7 layers and together answer whether 7 was a good choice.

E15/E16  SHAPE, WIDE BRACKET   budget 40K each  ~3.8 h each
     E15  --n_layers 3  --depth 17 --clock_base 13.15   ladder 1,13,173
     E16  --n_layers 17 --depth 3  --clock_base 1.38    ladder 1,1,2,3,4,5,7,10,
                                                        13,18,25,35,48,66,91,125,173
     Why these and not only E07/E08: 5, 7 and 10 layers span less than a factor
     of two, which is too narrow to resolve a trend against sigma ~0.07.  3 and
     17 span a factor of ~6 and bracket the baseline properly.  If the wide
     points are flat, the dimension does not matter and E07/E08 can be dropped
     entirely -- which would itself be a useful result, since 7x7 was inherited
     from the original brief and never justified.
     All hold n_layers*depth ~ 50 (29-31M params) AND p_max = 173 by
     renormalizing --clock_base, so neither parameter count nor reach is
     confounded with the shape.  This is three flags moving as one concept
     ("shape at fixed capacity and fixed reach"); labelled per section 4.
     Hypothesis: total conv depth is fixed at ~50, so what varies is how it is
     PARTITIONED -- many shallow registers with many timescales, versus few deep
     ones with few.  L=3 gives three timescales (1, 13, 173) and 17 convs of
     compute between them; L=17 gives sixteen distinct timescales and 3 convs
     each.
     Predict: an interior optimum, because the extremes fail differently -- L=3
     has too few timescales to cover [1,173], L=17 has too little compute per
     layer to transform the state usefully.  If so, 7x7 is probably near it and
     the dimension is settled cheaply.
     Falsified if: monotone in L across 3, 7, 17, which would say the partition
     matters and the search should push past whichever end wins.
     CAVEAT at L=17: base 1.38 is below the ~1.4 point where consecutive layers
     round to the same period, so the ladder has 16 distinct values not 17 (two
     layers share period 1).  Documented in --clock_base's help.  L=25 would be
     worse (21 distinct of 25) and is not proposed.

E09  --qproj read        budget 40K   ~3.8 h
     Hypothesis: a trainable 1x1 between the register and the feedback add lets
     a layer transform what it REMEMBERS differently from what it is TOLD -- the
     only option that targets the memory path specifically.
     TENSION: this re-introduces an unnormalized map into the recurrence, which
     is what removing --tap just eliminated.  Watch dff_max for the monotone
     climb signature (33 -> 63 -> 82 -> 101) that the tapped runs showed.
     Predict: better reach, higher runaway risk.

E10  --context 24        budget 40K   ~3.8 h
     Hypothesis: the state is n_hidden x context x context = 256x16x16 = 65K
     values.  24x24 nearly doubles it to 147K at ~2.2x the compute.  Capacity
     may be what is limiting the 6.08 plateau, not reach.
     Predict: better loss, worse tokens/second; judge on loss-vs-wallclock too.
     NOTE: changes param count (kernel convs are unchanged, but the pooled
     decoder sees a bigger grid), so it is not a pure control.

7b. GROWING THE QUEUE -- NEW EXPERIMENTS ARE EXPECTED, NOT EXCEPTIONAL
--------------------------------------------------------------------------------
E01-E12 is a starting list, not a fixed program.  The point of the search is that
each result should suggest the next question, and the most valuable experiments
are the ones that could not have been written down at the start.  After every
TERMINATE or PROMOTE, ask explicitly: what does this result make worth trying
that was not on the list?  Append it with the same discipline as the originals --
hypothesis, prediction, falsifier, budget -- and slot it into the order by
expected information per GPU-hour, so there is always a default next move.

Sources of new experiments, in rough order of how often they have paid off here:

  a) A RESULT THAT CONTRADICTS ITS PREDICTION.  The mechanism was misunderstood,
     so the neighbourhood of that option is unexplored.  E01 already did this:
     --ema 0.25 was predicted to converge more slowly and instead reached the
     unigram floor in 1280 steps against the baseline's 3980.  That immediately
     makes "how far does this go" (--ema 0.1, 0.05) worth asking, and it was not
     on the list.

  b) A KNOB THAT DOES NOT EXIST YET.  Proposing and implementing a new vla.py
     option is allowed and encouraged.  --clock_base, --clock_max, --clock_ends,
     --clip_dff and --tap_norm were all added mid-study because a measurement
     implied a quantity that had no flag.  Commit vla.py so every run is
     traceable and revertable, keep the default equal to the previous behavior
     so old checkpoints and invocations are unaffected, and put the new option
     in _ARCH_ARGS (and _ARCH_OVERRIDE if it adds no parameters) so --generate
     and --vis reproduce what was trained.

  c) A MEASUREMENT THAT CANNOT ANSWER THE QUESTION BEING ASKED.  Twice the right
     next step was a better probe rather than another training run: the reset-
     based reach probe conflated genuine long-range use with warm-up time, and
     teacher-forced loss could not see free-running collapse at all.  Probes are
     minutes of GPU where training runs are hours; when in doubt, measure better
     before training more.

  d) AN INTERACTION THE SINGLE-OPTION DISCIPLINE HIDES.  Options that are only
     meaningful together (--n_layers with --clock_base to hold p_max fixed;
     --ema with --clock_base since reach ~ kappa(ema)*p_max) need a deliberate
     paired experiment.  Do these rarely and label them clearly, since they cost
     the attributability that makes the rest of the search readable.

  e) A CONFIGURATION FROM AN EARLIER CORPUS THAT WAS NEVER RETESTED.  The
     TinyStories conclusions were drawn on 196-token documents and several did
     not survive the move to openwebtext.  Anything concluded on tiny is a
     hypothesis, not a fact, until it has been rerun on web.

8. TERMINATION
--------------------------------------------------------------------------------
Stop an experiment early when:
  - loss is >0.15 above baseline at the same step at two consecutive 5K marks
    (it is not going to recover), OR
  - generation is degenerate (cycle > 0.6) at two consecutive checkpoints, OR
  - the hypothesis has already been decided by the data collected so far.
Do NOT stop on a single bad runaway reading (see 3e) -- that mistake cost this
study a 100K tapped run.
Let an experiment run to its full budget when the gradient is still rising: that
means the deep stack is still organizing and the loss curve has not converged.

9. FINAL DELIVERABLE
--------------------------------------------------------------------------------
A single recommended command line, justified by:
  - final held-out clean loss, and the token count to reach each threshold
  - the reach curve, warm-context, with the runaway rate stated
  - generation health, with sample text
  - an explicit statement of which options were shown to matter, which were
    shown NOT to matter, and which remain untested.
Report ties as ties.  Prefer the simpler configuration on a tie.

10. PRIVATE / CROSS-SESSION STATE

This section is the bridge between sessions.  A fresh session should be able to
read PLAN.txt plus ./log and ./checkpoint and pick up the hypothesis chain with

LAYOUT
  ./checkpoint/   all weights.  New runs save checkpoint/<mnem>.pt.  79 legacy
                  files were moved here 2026-08-21 keeping their original names
                  (checkpoint.pt.<n>, checkpoint.pt.w*, checkpoint.pt.s*, ...).
                  git-ignored: 13 GB.
  ./log/          exp.<mnem> is the vla.py log, exp.<mnem>.out the stdout.
  ./exp/          run.sh (baseline + overrides), report.sh (appends a 5K report
                  to this file), score.py, reach.py, gencheck.py, memtest.py,
                  genstate.py, ckpt_report.sh.
  vla.py committed at e0ec0a4 with all new options.

HOW TO RUN AN EXPERIMENT
  ./exp/run.sh <mnem> <steps> <overrides...>     # baseline is wnotap, see sec 1
  ./exp/report.sh <mnem> <expid>                 # after each 5K checkpoint

TOOL NOTES THAT COST TIME TO LEARN
  - Always read checkpoints through score.py's stable_load().  torch.save is not
    atomic; a mid-write read scores as a broken model WITHOUT raising.  This
    produced a bogus 100%-runaway reading that caused a healthy run to be
    cancelled.
  - nvidia-smi is NOT a liveness check.  --dataset web non-streaming spends
    ~4.5 min memory-mapping 80 arrow shards holding no GPU memory, so the GPU
    reads 15 MiB while a trainer is very much alive.  Use
    pgrep -f "python vla.py".  Launching a second run on top of a live one makes
    both append to the same log.
  - Use --streaming for anything under ~1 hour; non-streaming only for long runs.
  - gencheck.py must set MKL_THREADING_LAYER=GNU on the child process or it
    exits rc=1 with no stdout.
  - vla.py --load PREPENDS the checkpoint's embedded log to the new log file.
    So `head` on a resumed log shows the OLD run's ARGS.  Always read the tail.
  - Killing runs: pkill -f patterns match this shell's own command line.  Get
    pids with pgrep first, then kill -9 by number, then verify with pgrep -c.

MISTAKES MADE, SO THEY ARE NOT REPEATED
  - Called a trend from two points three times.  Runaway rate is NON-MONOTONE:
    wfix236 went 1.8 -> 1.0 -> 100 -> 40.5 -> 8.0 across 20/40/50/60/65K and
    wnotap went 0.2 -> 46.2 -> 0.8 -> 1.2 -> 3.8.  A 100K tapped run was
    cancelled on the strength of one reading that was already receding.
  - Reported a mean over an unbounded quantity.  A model with 3 runaway rows in
    250 showed "held-out loss 1.4e9" while being fine on the other 247 (4.008).
    Always report clean/median AND the runaway rate, never a naive mean.
  - Over-read single temperature-1.0 samples as evidence of progress or
    regression.  Use gencheck.py's 3-sample cycle score for anything load-bearing.
  - Claimed --clock exp had a runtime penalty; it did not.  The measurement was
    contaminated by probes I was running concurrently on the same GPU.

OPEN QUESTIONS THE SEARCH SHOULD EVENTUALLY ANSWER
  - Does anything lift the ~6.08 held-out plateau, or is 29.4M params on 16x16
    the ceiling?  E10 (--context 24) and E05 (--schedule cosine) are the two
    candidates that attack it from different directions.
  - Is reach worth anything on loss?  Every measurement so far says the two
    trade against each other, and the reach/loss frontier has never been mapped.
  - Are the runaway excursions the same phenomenon as the free-running
    generation collapse?  genstate.py showed generation collapse IS a state
    explosion (10x per 5 tokens); whether the teacher-forced excursions share
    that mechanism is untested.

11. RUNNING LOG  (a DECISION at every 5K checkpoint, not just a report)
================================================================================
At every 5K checkpoint, do all five:
  1. READ the auto-emitted numbers below, AND the raw log (grad direction,
     dff_max/dff_std divergence, dff_zeros), AND any score/reach results.
  2. COMPARE against the wnotap baseline at the SAME step (section 2) and
     against this experiment's own prediction and falsifier as written down
     before it started.
  3. DECIDE one of:
       CONTINUE  -- the hypothesis is still live and the budget is not spent
       EXTEND    -- gradient still rising / curve not converged, add 5K blocks
       TERMINATE -- decided, or failing the section 8 stop rules; go to the
                    next queued experiment
       PROMOTE   -- wins on the section 6 rules; it becomes the new baseline and
                    the remaining queue is re-derived against it
  4. WRITE the reasoning here as a COMMENTARY block and post the same to the
     console.  State explicitly when a result contradicts the prediction --
     that is the most informative outcome and the easiest to quietly drop.
  5. ASK WHAT THIS RESULT MAKES WORTH TRYING that was not already on the list,
     and if there is something, append it to the queue now (section 7b) with
     hypothesis / prediction / falsifier / budget, slotted by expected
     information per GPU-hour.  Do this at EVERY checkpoint, not only at the end
     of an experiment: a mid-run observation is often the one that suggests the
     next question, and it is lost if it is not written down when it is noticed.
     "Nothing new" is a valid answer, but it should be a considered one.
Re-order the queue after every TERMINATE or PROMOTE so there is always a default
next experiment if the current one turns out inconclusive.

E17  --init zero    budget 20K, extendable   NEXT
  Motivation (user, 2026-08-21): with 3x3 pad=1 convs the zero padding lets the
  CNN learn positional information automatically.  This matters more here than in
  a normal CNN because _tok_grid broadcasts the token UNIFORMLY to all SxS
  positions -- the input carries no spatial structure at all.  So the only two
  things that can distinguish one position from another are the --init seed and
  the padding.  RF radius is 49 against a 16-wide grid, so every position knows
  its distance to every border: padding supplies a complete positional code and
  the DFF state is an ADDRESSABLE memory, not just capacity.
  Hypothesis: --init gaussian overwrites that deterministic, free positional code
  with fresh random noise at every context reset -- every ~890 tokens on web.  The
  model then has to see through a different noise pattern each document.  --init
  zero leaves padding as the sole source of spatial structure, identical at every
  document start.
  Supporting evidence already in hand: dff_zeros starts at 0.5057 under gaussian
  and collapses to ~0.026 within 10K steps, i.e. the model spends capacity
  suppressing the seed; and every runaway excursion begins at a fresh context,
  which is exactly where the seed enters.
  Predict: faster to L<7.0 than baseline's 5940 steps, loss lower or equal,
  possibly fewer runaway excursions.
  Falsified if: slower to L<7.0 than 5940, which would mean the random seed
  provides symmetry breaking that padding cannot.
  Note it REMOVES a mechanism rather than adding one, which suits the FPGA

  computed since its last write, instead of the single output from the step it
  writes on.  At clock_base 2.36 the deepest layer holds 173 steps, so it is
  averaging up to 173 outputs -- heavy smoothing, and one extra DFF-sized buffer

  exist to carry.  Sampling one output instead may sharpen them.

  Falsified if: loss clearly worse at 20K AND 30K, i.e. the mean is doing real
  denoising that a single sample cannot replace.

  NOTE on --accumulate storage (user asked): it IS a second buffer per layer,
  self.acc[li] = torch.zeros_like(o), same shape as the register, not an in-place

  between writes because _fb() reads it as feedback every step, so if the

  which is the whole point of the clock.  --ema is the in-place variant and needs

  > 1, and being a plain sum of ReLU outputs divided once it could be lower
  precision or integer.

13. WEIGHT DECAY STUDY  --  CANCELLED, superseded by section 14 (--norm none)
================================================================================
Runs after E30.  Capacity (--n_hidden, --kernel) is deferred to LAST by user
direction, so weight decay is the next dimension.

WHY IT IS INTERESTING HERE, AND WHY THE OBVIOUS ARGUMENT IS WRONG:
ContextCNN is Conv -> BatchNorm2d(affine=False) -> ReLU throughout, and weight
decay on a conv that is immediately BatchNormed does NOT shrink the function --
BN renormalizes the scale away, so decay only changes the EFFECTIVE learning
rate.  That is the standard result and it would make this study pointless...
except that this architecture has convs with NO normalization after them:
    text_proj    (c_text -> n_hidden, 1x1, the token injection)
    deep_proj    (n_hidden -> n_hidden, 1x1, between stacked layers)
    decoder.proj (n_hidden -> c_text, 1x1, the readout)
Those three are the only unnormalized maps left after --tap was removed, and
deep_proj sits directly on the feedback path.  Weight decay genuinely shrinks
them.  So this measures something real and specific: what happens when the
unnormalized parts of the recurrence are pulled toward zero.

SECOND REASON, from the E30 result: the loss has FLATTENED (5.580 -> 5.562 ->
5.569 across 80K-120K) with dff_max steady at 10-13.  A converged run is exactly
where a regularizer can show a benefit that a still-descending run would hide.

BASELINE for this study: 3x17, lr 0.03, --init zero, --ema 0.5, --accumulate,
weight_decay 0.0.  Reference numbers come from E29/E30.

  E31  --weight_decay 1e-4   20K   the conservative point
  E32  --weight_decay 1e-3   20K   10x
  E33  --weight_decay 1e-2   20K   100x; expected to be too strong

PREDICT: 1e-4 indistinguishable, 1e-3 the interesting one, 1e-2 clearly worse.
  If any value wins, the mechanism is the three unnormalized 1x1 convs, and the
  follow-up is to decay ONLY those (would need a new flag, e.g. --wd_proj) --
  which would be a cleaner intervention than global decay, since decaying the
  BatchNormed convs is just an lr change in disguise and lr is already tuned.
FALSIFIER: all three within sigma of baseline, i.e. weight decay does nothing
  here because the BN-invariant convs dominate the parameter count (3x17 has 51
  BatchNormed convs at 590K each against 3 unnormalized 1x1s at 66K each -- the
  decayable fraction is only ~0.6% of parameters).  That is the most likely
  outcome and worth recording either way.
NOTE: because weight decay under BN acts as an effective-lr change, a wd result
  must be read against the KNOWN lr sensitivity: lr 0.03 is 0.12 better than
  0.02 and 0.04 is BROKEN.  A wd that helps may simply be nudging the effective
  lr, so any winner must be re-checked at a slightly different lr before being
  attributed to regularization.

14. NO-BATCHNORM STUDY  (user-directed, 2026-08-23).  vla.py commit eced110.
================================================================================
Weight decay is CANCELLED.  The reason it looked interesting was that only three
convs in the model are unnormalized, so decay could act on them specifically --
but that is a ~0.6% slice of the parameters.  Removing BatchNorm attacks the same
structure from the other side and is far more consequential.

--norm none: ContextCNN becomes Conv2d -> ReLU.  He init (kaiming_normal, fan_in,
relu gain) replaces PyTorch's default, which has a gain far below 1 for ReLU and
would shrink the signal ~3x per layer -- over 51 layers that reaches the readout
as nothing.  Verified: block = [Conv2d, ReLU], ZERO buffers (vs 34 running-stat
entries per block), same parameter count, in std 1.01 -> out 0.65 over 2 layers
(BatchNorm: 0.99 -> 0.58), so the init preserves variance comparably.

WHY THIS IS THE MOST IMPORTANT REMAINING EXPERIMENT
BatchNorm is the ONLY module here whose function differs between train and eval,
and the recurrence amplifies that difference every step.  Every pathology in this
study traces to it:
  - --no-accumulate: train 6.36, held-out 9.23 (2.9 nats), all other metrics clean
  - --lr_max 0.04:   best training loss ever recorded here, held-out 9.82 (3.4)
  - free-running generation locking into a repeating token while training-time
    metrics stayed clean (genstate.py showed the state growing 10x per 5 tokens)
  - the runaway excursions, where the state amplifies under FROZEN running stats
--norm none makes train and eval the same function by construction, so these are
removed rather than managed.  It also deletes the running-statistics buffers,
which are real state in an FPGA dataflow.

RISK, stated plainly: BatchNorm is what makes a 51-conv chain trainable at all.
A plain deep chain may simply fail to train, or need a much lower lr.  That is
the experiment.

DESIGN (user, 2026-08-23): focus on the INITIAL STEPS TO BREAKTHROUGH, and try
momentum and especially ADAMW.  Rationale for both:
  - Breakthrough is make-or-break for a no-BN deep chain.  Every run in this study
    crosses the 7.549 unigram floor between 1.2K and 6K steps; if --norm none is
    going to fail, it fails there.  So the grid is SHORT runs (10K) scored on
    steps-to-breakthrough, not long runs scored on final loss.
  - ADAMW IS THE INTERESTING ONE.  AdamW failed badly WITH BatchNorm: it parked at
    the unigram floor for thousands of steps with dff_max reaching 3.7e5.  The
    mechanism was BN scale-invariance -- BN makes the conv weights' scale
    irrelevant to the function, so those directions are loss-neutral, and AdamW's
    per-parameter normalization promotes exactly the loss-neutral directions to
    full-size lr steps.  Remove BN and that pathology has no cause.  AdamW may
    now be the better optimizer, and it was rejected on evidence that no longer
    applies.
  - Momentum was likewise only ever tested with BN present.

GRID, 10K each (~55 min), all --norm none at the promoted 3x17 baseline.
ORDERED MOST-NOVEL-FIRST: the adamw and momentum runs can OVERTURN a dimension
this study closed on day one, while the sgd points mostly confirm what is known.
If time runs short, sacrifice the sgd tail, not the head.

PROCESS FIX  2026-08-23 12:05  -- after a 90-minute silent GPU stall

WHAT HAPPENED: exp/nobn.sh was edited WHILE RUNNING to insert E37/E38 ahead of
the SGD tail.  Bash reads a script incrementally by byte offset; the insertion
shifted every later offset, bash resumed at the shifted position, and it executed
the OLD E31/E32/E33 lines instead of the inserted ones.  It then printed
"NOBN GRID COMPLETE" and exited.  The session was waiting on a watcher for E37,
which had never been queued, so nothing noticed and the GPU sat idle 10:36-12:03.
This failure mode was already known in this session -- phase1.sh was deliberately
NOT edited while running, for exactly this reason -- and the lesson was not
carried forward.

FIX 1: exp/launch.sh <driver.sh> [args]
  Copies the driver to exp/.run/<name>.<timestamp>.sh and execs the SNAPSHOT.
  The running job can no longer be affected by edits to the source, and the
  snapshot is a permanent record of exactly what was executed.
  USE THIS FOR EVERY DRIVER FROM NOW ON.  To change a queue mid-flight, edit the
  source and relaunch, or write a NEW driver -- never edit the live one.

FIX 2: exp/idle_watch.sh, armed as a persistent Monitor
  Emits a notification after 5 consecutive minutes with no `python vla.py`
  running, then every 15 minutes while it persists, along with the last line of
  each driver log so the cause is visible immediately.
  This is the general fix: it catches ANY stall -- driver exited early, trainer
  crashed, chained job whose predecessor never signalled, a waiter armed on a
  filename that does not exist -- not just the edit-a-running-script bug.
  A stalled GPU is the one failure that costs time silently; everything else
  produces a wrong number that gets caught by the next score.

NOT WASTED: the accidental E31/E32/E33 runs completed the optimizer picture for
--norm none.  Every SGD variant NaNs within 4-8 steps (E31 lr 0.03 step 7,
E32 lr 0.01, E33 lr 0.1 step 4, E34 momentum step 8), while AdamW survives.
So plain SGD cannot train this architecture without a normalizer at ANY lr
tried, and AdamW's per-parameter normalization is doing part of the job
BatchNorm used to.
